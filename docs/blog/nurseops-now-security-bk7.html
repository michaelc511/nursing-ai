Why this post

What this covers. Security for an AI agent (an AI that chooses which tools to use to answer), in four parts after an intro: the main threats, injection (hidden text that tries to give the AI new orders) and data leaks (13.1); jailbreaks (talking the AI out of its safety rules) and disguised attacks (13.2); risks from libraries, APIs and tools (a function the AI can call, such as policy search) the agent (an AI that chooses which tools to use to answer) depends on (13.3); and the hardening patterns that limit damage when something gets through (13.4). A closing playbook turns it into a checklist. For each part I state (everything the app must remember to continue correctly) the problem and how NurseOps Now solves it, with the real code and real output, what isn't built yet, and where I'd push back on common advice.

How this differs from the other posts. The eval plan proves the answers are good, and its red team (people or scripts that try to trick the AI on purpose) proves attacks don't get through. The state post covers what the AI remembers and what must never be saved. This post is about what an attacker can make the agent (an AI that chooses which tools to use to answer) do: who can send it orders, what it is allowed to touch, and what happens when one check fails. Each step has the usual two halves: the strategy (what we built) and the proof (how it's checked).

In plain terms: a security walk-through of a building: who gets in, what each key opens, and what still holds if a door is left open.

1. Problems I hit: The RCE Paradox, Privilege creep, One guardrail is never enough, The "Summarization" Trap, Markdown Image Exfiltration → Architect defense-in-depth strategies using sandboxing and least-privilege principles to contain breaches. 🟡 What I built: checks in code before and after Claude (Anthropic's AI model that this app uses); the AI can read but never decide; no tool (a function the AI can call, such as policy search) runs code; chat answers are shown as plain text. Not yet: an egress filter (a block on outbound traffic except to approved hosts), canary tokens (a fake secret that raises an alarm if it ever shows up), short-lived scoped access. (13.1, 13.4)

Solutions behind it (click a name to jump to its row below; hover for a one-line meaning):

  • Segmentation (Least Privilege) ✅: AI tools (a function the AI can call, such as policy search) read only; only people decide (13.1)
  • Monitoring (Anomaly Detection) 🟡: rate limit (a cap on how many requests one user can make per minute), cost caps that pause the AI, traces (step-by-step records of each request: what ran, how long, what it cost) and audit rows (one line in the log of who did what, when); no anomaly alarm (13.1)
  • Protocol A: The Principle of Least Privilege (PoLP) 🟡: roles and a human-only state machine (a fixed list of allowed status changes); tokens (pieces of words the AI reads and writes; cost is per token) last 12 hours, not minutes (13.4)
  • Protocol C: Defense in Depth (The Swiss Cheese Model) ✅: ingress, prompt (the instructions and text given to the AI) and egress (traffic going out of the app to other hosts) checks, each in code (13.4)
  • Egress Filtering (Allowlisting) ⬜ and Canary Tokens (Honeytokens) ⬜ (Playbook)

2. Problems I hit: Instructions and data share one channel, Direct Injection (Jailbreaking), Prefix Injection → Immunize against Prompt Injection (hidden text that tries to give the AI new orders) by separating system instructions from user data (the instruction hierarchy (rules in the strongest place; outside text clearly marked as data)). ✅ What I built: the rules go in the API's separate system field; documents are wrapped in tags and labeled data; tool (a function the AI can call, such as policy search) results come back as tool (a function the AI can call, such as policy search) results; the user can never write the start of the AI's answer. (13.1, 13.2)

Solutions behind it:

  • Wrap untrusted data in XML tags ✅: documents in <document>, policy (the health plan's written rules for when a test is covered) text in <policy_chunks> (13.1)
  • Never let the user dictate the start of the response ✅: messages are built on the server (13.2)
  • The Sandwich Defense (Instruction Hierarchy) 🟡: rules sent first on every call, no reminder after the data (Playbook)

3. Problems I hit: Indirect Injection (The Trojan Horse), Persona Masquerading (Roleplay), Obfuscation (Encoding), Adversarial Suffixes (The Math Hack), New jailbreaks every week → Harden input validation to treat all external text, including emails and websites, as potential attack vectors (text turned into lists of numbers so similar meanings sit close together). 🟡 What I built: a code gate (an automatic check that blocks a change when scores drop) on every question, a scan of every page of every patient document, and file type checks at the door; a red team (people or scripts that try to trick the AI on purpose) of 44 attacks in CI (continuous integration: tests that run automatically on every code change). Not yet: disguised attacks still get past the code gate (an automatic check that blocks a change when scores drop) (5 of 7 in today's demo). (13.1, 13.2)

Solutions behind it:

  • Input Sanitization (The Air Gap) 🟡: done with code checks, not a sanitizer model (13.1)
  • Pattern Matching (Vector Shielding) 🟡: known attacks matched with patterns, not embeddings (text turned into numbers so similar meanings sit close together) (13.2)
  • Input Paraphrasing (The "Smoother") ⬜ and Perplexity Filtering (The Noise Detector) ⬜ (13.2)
  • Output Guardrails (Refusal Enforcement) ✅: secrets, prompt (the instructions and text given to the AI) leaks and decision claims caught before anyone sees them (13.2)
  • Protocol D: Continuous Red Teaming 🟡: 44 attacks on every push, not 1,000 (13.4)

4. Problems I hit: The "PyPI" Poisoning (Library Risk), Response Injection (The API Trojan), The "Zombie" Agent → Audit (a permanent record of who did what and when) the tool (a function the AI can call, such as policy search) supply chain (the outside libraries and services an app is built on) to prevent third-party vulnerabilities from escalating into full system compromise. 🟡 What I built: the AI's tools (a function the AI can call, such as policy search) are my own services, not outside APIs; the frontend is locked with hashes; the app runs in a Fly.io (the cloud service that hosts the live app) micro-VM (a tiny virtual machine that starts in milliseconds) and refuses to start without its secrets. Not yet: hash-pinned Python packages, a CVE (a publicly listed security hole in a piece of software) scan, an egress filter (a block on outbound traffic except to approved hosts). (13.3)

Solutions behind it:

  • Verification of Dependencies 🟡: npm lockfile (a file listing the exact version (and hash) of every package) with hashes; Python versions in ranges (13.3)
  • The Sandbox Mandate ✅ by design: no tool (a function the AI can call, such as policy search) runs code (13.3)
  • The Egress Filter ⬜ and The Fix: "Sidecar Scanner" ⬜ (13.3)

Security and Robustness (Intro)

What it does. Explains why an agent (an AI that chooses which tools to use to answer) that can act is a bigger target than a chatbot, and what this app's answer is.

The problem. Once an AI can read files, call tools (a function the AI can call, such as policy search) and change records, a bad answer isn't just text: it's an action. And nobody has to break in to cause that action. They only have to persuade the agent (an AI that chooses which tools to use to answer), in plain language, which is much harder to patch than code. In a prior authorization (a health plan approving a test or treatment before it happens) app the worst outcomes are clear: an AI that approves or denies care on its own, or one that leaks patient data.

How NurseOps Now solves it.

  • The AI can't take the action that matters. It can never approve, deny or pend (pause a case for more information or a medical director). That's enforced in the service layer, not in the prompt (the instructions and text given to the AI) and not in the UI (Step 10).
  • Everything from outside is data. Questions, faxes, PDFs (a fixed-layout document file) and tool (a function the AI can call, such as policy search) results are checked in code and labeled as data in the prompt (the instructions and text given to the AI) (Steps 1–3).
  • Several layers, each in code where possible, so one miss isn't fatal (Protocol C).

In plain terms: the intern can read every file and draft every letter, but can't sign anything, and the mailroom opens every envelope before it reaches them.

The Threat Landscape: Injection & Exfiltration (13.1)

What it does. Names the two big risks, injection (hidden text that tries to give the AI new orders) (getting new orders in) and exfiltration (getting private data out of a system) (getting private data out), and the first line of defense against each.

The problem:

  1. Instructions and data share one channel: the model can't tell the rules from the text it's reading.
  2. Direct Injection (an attack typed straight into the chat) (Jailbreaking (talking the AI out of its safety rules)): the user types the attack.
  3. Indirect Injection (an attack hidden inside a document or tool result the AI reads) (The Trojan Horse): the attack hides in a document the AI reads, which is the dangerous one here, because faxes come from outside.
  4. The "Summarization" Trap: asking the AI to repeat what it just read, to pull out secrets.
  5. Markdown Image Exfiltration (getting private data out of a system): an image link that sends a secret to another server when the browser loads it.

How NurseOps Now solves it (the standard solutions first, then mine):

  • Input Sanitization (The Air Gap) (cleaning outside text before the main AI sees it) 🟡: code checks, not a sanitizer model (Step 1, Step 3).

  • Monitoring (Anomaly Detection) (watching usage and stopping the AI when something looks wrong) 🟡: limits and caps, no alarm (Step 12).
  • User Education (Expectation Management) (telling users what the AI can and can't be trusted with) 🟡: labels, sources, "please check" (Step 5).
  • Wrap untrusted data in XML tags ✅ (Step 2).
  • Document scan and plain-text answers (ours) ✅ (Step 3, Step 4).

Common advice vs. NurseOps Now

Common advice I'd correct:

  • "Scan the output for 'I cannot' or 'I'm sorry'." Those phrases mean the AI refused, which is the good outcome.   • "Survive 1,000 attacks with 0% success or fail the build." Fair when the pass check is code (no status changed, no key in the answer), as in Step 13. Noisy when another AI grades the answers.
  • "Docker isn't enough; use micro-VMs (a tiny virtual machine that starts in milliseconds)." True for running AI-written code. The bigger win here was not having that tool (a function the AI can call, such as policy search) at all.

What this proves

NurseOps Now assumes the AI will be tricked and makes sure it doesn't matter much when it is. Outside text is checked in code and fenced as data, answers are checked in code before anyone sees them, and the one action that matters, approving or denying care, is impossible for the AI because only a person can do it, in the service layer. Today's demo also shows where it's weakest: the code gate (an automatic check that blocks a change when scores drop) misses disguised attacks. That gap, along with supply-chain checks, canaries and an egress filter (a block on outbound traffic except to approved hosts), is named, with a plan for each.

All cases and people are synthetic (made up for the demo; no real patients). No real patient data is used.
