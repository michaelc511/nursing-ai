In plain words

LangGraph (a tool for building AI workflows step by step) builds an AI app as a graph of steps (nodes) that share a state (everything the app must remember to continue correctly). Its memory story is two pieces: a checkpointer (the code that saves a checkpoint after each step) that saves each conversation (thread (one saved conversation, here one per user and case)) after every step, and a Store for long-term memories shared across conversations.

In plain terms: a notebook per conversation that saves itself after every line, plus a shared filing cabinet per user.

What it gives you for memory

From the official memory docs (LangGraph memory docs), checked on Nov 19, 2026:

  • Short-term: messages in graph state (everything the app must remember to continue correctly), saved per thread_id; trim with trim_messages (by tokens (pieces of words the AI reads and writes; cost is per token)) or delete with RemoveMessage.
  • Persistence: checkpointers (the code that saves a checkpoint after each step) InMemorySaver, SqliteSaver, PostgresSaver, MongoDBSaver, RedisSaver (and more); get_state, get_state_history, resume with invoke(None, config); durability modes; EncryptedSerializer for encryption at rest (a common way for programs to talk over the web using URLs).
  • Long-term: Store (InMemoryStore, PostgresStore, RedisStore, …) with tuple namespaces like (user_id, "memories"), put / get / search, optional semantic search with an index.
  • Summarizing: LangMem's SummarizationNode, or your own summary key.
  • Deleting: checkpointer.delete_thread(thread_id); no built-in TTL (the docs suggest a cron job).

How to implement it (ServiceApps)

Illustrative example: made-up data, no ServiceApps (a company platform for IT tickets, HR requests and help-center articles) instance. The code was run as shown; the model is a scripted stand-in, so no API key (a secret code that lets the app use a paid service) is needed.

The scenario. ServiceApps (a company platform for IT tickets, HR requests and help-center articles) Assist as a one-node graph: each conversation is a thread (one saved conversation, here one per user and case) (u42:INC0012345), the user's saved preference is in the Store, and only the last ~60 tokens (pieces of words the AI reads and writes; cost is per token) of chat are sent.

Steps.

  1. Compile the graph with a checkpointer (the code that saves a checkpoint after each step) (persistence) and a Store (long-term memory).
  2. Pass thread_id (conversation) and user_id in the config on every call.
  3. In the node, trim the messages by tokens (pieces of words the AI reads and writes; cost is per token) and read the user's memories from the Store.
  4. Delete a conversation with checkpointer.delete_thread().

The code (Python):

from langchain_core.messages import AIMessage, HumanMessage, trim_messages
from langchain_core.messages.utils import count_tokens_approximately
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.graph import START, MessagesState, StateGraph
from langgraph.store.base import BaseStore
from langgraph.store.memory import InMemoryStore

RULES = "You are ServiceApps Assist. Cite KB numbers."

def respond(state: MessagesState, config, *, store: BaseStore):
    user = config["configurable"]["user_id"]
    window = trim_messages(state["messages"], strategy="last", token_counter=count_tokens_approximately,
                           max_tokens=60, start_on="human")                 # short-term limit (7.1)
    prefs = [i.value["text"] for i in store.search((user, "memories"))]   # long-term memory (7.3)
    # a real node would call the model with RULES + prefs + window; here we report what it would send
    return {"messages": [AIMessage(f"(would send {len(window)} of {len(state['messages'])} messages; memories: {prefs})")]}

builder = StateGraph(MessagesState)
builder.add_node("respond", respond)
builder.add_edge(START, "respond")
store = InMemoryStore()
graph = builder.compile(checkpointer=InMemorySaver(), store=store)            # persistence + long-term store

store.put(("u42", "memories"), "pref-1", {"text": "prefers short bullet answers"})
cfg = {"configurable": {"thread_id": "u42:INC0012345", "user_id": "u42"}}
for q in ["My VPN shows error 809", "I'm on hotel Wi-Fi", "Still failing on my hotspot"]:
    out = graph.invoke({"messages": [HumanMessage(q)]}, cfg)
    print(f"{q!r:32} -> {out['messages'][-1].content}")

print("saved in thread:", len(graph.get_state(cfg).values["messages"]), "messages")
new = {"configurable": {"thread_id": "u42:general", "user_id": "u42"}}
print("new thread, same user:", graph.invoke({"messages": [HumanMessage("Hi")]}, new)["messages"][-1].content)
graph.checkpointer.delete_thread("u42:INC0012345")
print("after delete_thread:", graph.get_state(cfg).values.get("messages", []))

What to watch for.

  • Use SqliteSaver / PostgresSaver in production; InMemorySaver loses everything on restart.
  • Mask personal data before it reaches state (everything the app must remember to continue correctly) or the Store; LangGraph (a tool for building AI workflows step by step) doesn't redact.
  • Plan retention yourself: delete old threads (one saved conversation, here one per user and case) on a schedule.

Use both: what you still build

Still yours with LangGraph (a tool for building AI workflows step by step):

  • The Engineering Trade-off: Fidelity vs. Capacity (the trade-off between keeping every detail and fitting more in the window): No hard/soft split; your exact facts belong in your own tables
  • Structured Storage (SQL/Postgres) (a database with fixed tables for exact facts): PostgresSaver stores checkpoints (saved copies of a conversation's state), not your business tables
  • Sanitization layer (code that masks personal details and secrets before anything is saved): No redaction; EncryptedSerializer encrypts checkpoints (saved copies of a conversation's state) at rest (a common way for programs to talk over the web using URLs)
  • TTL (time-to-live) expiration (deleting saved data automatically after a set time): No built-in TTL in the docs; they suggest a cron job to delete old checkpoints (saved copies of a conversation's state)
  • Engineering Fix: Strict RAG and Citation Enforcement (answering only from retrieved sources, and flagging any answer without one): Retrieval (finding the right section of the right policy) tools (a function the AI can call, such as policy search) yes; checking citations (pointers to the exact page and quote that support each claim) is yours

In NurseOps Now

Used today: AI Assist (the app's chat helper for staff questions) compiles its LangGraph (a tool for building AI workflows step by step) graph with SqliteSaver (backend/app/services/assist.py), one thread per user and case (each nurse's conversation about each case is saved separately), cleared with delete_thread(). Masking (pii.py), the 10-turn window and SQL facts are NurseOps' own. The next step would be the Store for long-term per-user memory.

Trade-offs

  • Most control and the best persistence story, but you write more of the flow yourself.
  • Short-term limits and summaries are your code (or LangMem), not automatic.

Interview answer

"In LangGraph (a tool for building AI workflows step by step) I use a checkpointer (the code that saves a checkpoint after each step) for per-thread memory, which saves after every step so a conversation survives restarts, and the Store for long-term memories by user namespace. I trim by tokens (pieces of words the AI reads and writes; cost is per token) in the node, mask before saving, and delete threads (one saved conversation, here one per user and case) on a schedule because there's no built-in TTL."
