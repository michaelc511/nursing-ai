In plain words

LlamaIndex is best known for RAG (retrieval-augmented generation: the AI looks things up before it answers) over documents, and its agents (an AI that chooses which tools to use to answer) get a Memory object per session: recent chat is kept up to a token (the unit the AI reads and is billed by, about three quarters of a word) limit, and older messages are flushed into long-term memory blocks (static text, extracted facts, or a vector store (a database that finds text by meaning, using embeddings)).

In plain terms: a notepad with a size limit; when it's full, the oldest notes are filed into labeled binders, and one sticky note (the rules) is always on top.

What it gives you for memory

From the official memory docs (LlamaIndex memory docs), checked on Nov 19, 2026:

  • Short-term: Memory.from_defaults(session_id=..., token_limit=...); past chat_history_token_ratio, the oldest messages are flushed (token_flush_size); tiktoken counts tokens (pieces of words the AI reads and writes; cost is per token) by default.
  • Long-term blocks: StaticMemoryBlock (always inserted), FactExtractionMemoryBlock(max_facts=...), VectorMemoryBlock(vector_store, embed_model, similarity_top_k); priority decides what's truncated first (0 = never).
  • Persistence: an in-memory SQLite chat store by default; a remote SQL database via async_database_uri; workflow state (where an article is in its life: draft, review, published or retired) with ctx.to_dict() / Context.from_dict().
  • Older classes (ChatMemoryBuffer, ChatSummaryMemoryBuffer, VectorMemory) are deprecated in favor of Memory.
  • Deleting: chat-store level (delete messages by session); no TTL.

How to implement it (ServiceApps)

Illustrative example: made-up data, no ServiceApps (a company platform for IT tickets, HR requests and help-center articles) instance. The code was run as shown; the model is a scripted stand-in, so no API key (a secret code that lets the app use a paid service) is needed.

The scenario. ServiceApps (a company platform for IT tickets, HR requests and help-center articles) Assist with a 60-token memory and a pinned rules block: after seven messages, only the newest chat still fits next to the rules.

Steps.

  1. Create Memory.from_defaults(session_id=..., token_limit=...) per conversation.
  2. Add a StaticMemoryBlock with priority=0 for the rules (never truncated).
  3. Add a FactExtractionMemoryBlock or VectorMemoryBlock to keep what gets flushed.
  4. Point it at a real database (async_database_uri) in production.

The code (Python):

from llama_index.core.llms import ChatMessage
from llama_index.core.memory import Memory, StaticMemoryBlock

rules = StaticMemoryBlock(name="rules", static_content="You are ServiceApps Assist. Cite KB numbers.", priority=0)
memory = Memory.from_defaults(session_id="u42:INC0012345", token_limit=60,         # short-term limit (7.1)
                              chat_history_token_ratio=0.5, token_flush_size=20,
                              memory_blocks=[rules])                                # pinned rules (7.1)
turns = [("user", "My VPN keeps dropping on my laptop at the hotel"), ("assistant", "Which error code do you see?"),
         ("user", "Error 809 every time I connect"), ("assistant", "809 means the VPN can't reach the server."),
         ("user", "I'm on the hotel guest Wi-Fi right now"), ("assistant", "Avoid guest Wi-Fi; try your phone hotspot."),
         ("user", "Still failing on the hotspot too")]
for role, text in turns:
    memory.put(ChatMessage(role=role, content=text))
sent = memory.get()                                    # what the next model call receives
print("stored messages :", len(memory.get_all()))
print("sent next call  :", len(sent), "messages")
print("first one sent  :", sent[0].role.value, "->", str(sent[0].content)[:90])
print("oldest chat sent:", [m.content for m in sent if m.role.value == "user"][0])

What to watch for.

  • Without a fact or vector (text turned into a list of numbers so similar meanings sit close together) block, flushed messages simply leave the window.
  • The default store is in memory: configure a database for anything that must survive a restart.
  • No redaction or TTL: mask before put() and clean up by session.

Use both: what you still build

Still yours with LlamaIndex:

  • Textual Summarization (rewriting old conversation into short, dense notes): The summary buffer is deprecated; old messages are flushed to memory blocks instead
  • The Engineering Trade-off: Fidelity vs. Capacity (the trade-off between keeping every detail and fitting more in the window): Fact extraction is an LLM (large language model: the AI that reads and writes text (here, Claude)) rewrite: keep exact facts elsewhere
  • Structured Storage (SQL/Postgres) (a database with fixed tables for exact facts): A SQL chat store holds messages, not your records
  • Sanitization layer (code that masks personal details and secrets before anything is saved): Not on the memory page
  • TTL (time-to-live) expiration (deleting saved data automatically after a set time): Not mentioned
  • Input Filtering: Relevance Pruning (checking and trimming a question before the AI sees it): Yours

Use both (complement), with your rules on top:

  • Three-Tier Memory: Episodic (Experience Log) (a record of what happened, step by step): The chat store keeps messages per session; the audit log (a permanent record of who did what and when) is yours
  • Agentic Outcome: Strict State Serialization (saving state so work can pause, crash and resume without loss): Workflow (a fixed series of steps the app runs) ctx.to_dict() / Context.from_dict(); Memory is stored separately
  • Rolling Summaries (a short running summary that replaces old conversation turns): Past chat_history_token_ratio, the oldest messages move to long-term blocks
  • The Hot/Cold State Architecture (splitting memory into what is in the current call (hot) and what is saved for later (cold)): Short-term chat is hot; memory blocks are cold
  • GDPR Right to Be Forgotten (a person's right to have their stored data deleted (from the EU's GDPR law)): Delete messages in the chat store by session
  • Engineering Fix: Recursive Goal Injection (repeating a short reminder of the rules before every AI answer): A StaticMemoryBlock reminder is inserted every turn
  • Engineering Fix: Strict RAG and Citation Enforcement (answering only from retrieved sources, and flagging any answer without one): Citation-style query engines return numbered sources; checking them is yours
  • Process Control: Self-Correction Loop (checking the AI's answer and sending it back once to fix what failed): Workflows (a fixed series of steps the app runs) can loop back; the check is yours

In NurseOps Now

Not used in NurseOps Now; its RAG (retrieval-augmented generation: the AI looks things up before it answers) is built directly on Chroma (the database that stores the policy vectors) and sentence-transformers (a library that turns text into vectors).

Trade-offs

  • The best built-in token (the unit the AI reads and is billed by, about three quarters of a word) window plus long-term blocks, and strong RAG (retrieval-augmented generation: the AI looks things up before it answers), but persistence and deletion are lower-level.
  • Fact extraction is an LLM (large language model: the AI that reads and writes text (here, Claude)) rewrite: useful, but not a record of truth.

Interview answer

"In LlamaIndex I'd use Memory per session with a token (the unit the AI reads and is billed by, about three quarters of a word) limit, a static block with the rules at priority zero so they're never cut, and a fact or vector (text turned into a list of numbers so similar meanings sit close together) block to catch what overflows. It's the best built-in window management of the four; persistence and deletion I'd wire to our own database."
