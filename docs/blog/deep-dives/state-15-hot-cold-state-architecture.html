In plain words

Hot state (what is in the current AI call) is what the AI is working with right now, in memory for this call. Cold state (what is saved in a database for later) is what's saved in a database for later: preferences, history, finished tasks. Each call loads the bit of cold state (what is saved in a database for later) it needs into hot state (what is in the current AI call), and saves what matters back.

In plain terms: hot is what's on your desk today; cold is the filing cabinet.

The problem it solves

Summarization solves volume, not time (a summary shrinks memory but doesn't survive a crash or restart): if everything lives (using the real Claude API (costs money), not a fake stand-in) in the window, a crash, a closed tab or a new session loses it.

The standard approach (in my words): separate hot state (what is in the current AI call) (context window (everything sent to the AI in one call; it has a size limit) and RAM: fast, volatile, current reasoning) from cold state (what is saved in a database for later) (SQL, NoSQL or a vector (text turned into a list of numbers so similar meanings sit close together) database: durable, slower, long-term facts).

How to implement it (ServiceApps)

Illustrative example: no ServiceApps (a company platform for IT tickets, HR requests and help-center articles) instance is connected, so the scenario and data are made up. The code is a self-contained sketch; it was run on that made-up data on Nov 19, 2026, and the output below is from that run.

The setting. ServiceApps (a company platform for IT tickets, HR requests and help-center articles) Assist, an AI helper inside a company's ServiceApps (a company platform for IT tickets, HR requests and help-center articles) portal. Employees ask it IT and HR questions; it answers from knowledge-base (KB (knowledge base: a library of help articles)) articles, looks up the employee's own tickets (incidents (a ServiceApps ticket for something broken) like INC0012345) and requests, and keeps one conversation per employee and ticket.

The scenario. ServiceApps (a company platform for IT tickets, HR requests and help-center articles) Assist answers "Is my laptop under warranty?" using a saved profile, with scratch notes that are thrown away after the call.

Steps.

  1. Keep a cold store (a database) for facts that must survive.
  2. At the start of a call, load the needed cold facts into hot state (what is in the current AI call).
  3. Keep scratch reasoning hot only.
  4. At the end, write back what should be remembered and clear hot state (what is in the current AI call).

The code (Python):

import sqlite3, json
cold = sqlite3.connect(":memory:")               # stand-in for the database
cold.execute("create table facts(user text, key text, value text, primary key(user, key))")
hot = {}                                         # in RAM: this call only

def remember(user, key, value):
    cold.execute("insert or replace into facts values(?,?,?)", (user, key, json.dumps(value)))

def start_call(user, question):
    hot.clear()
    hot["question"] = question
    hot["profile"] = {k: json.loads(v) for k, v in cold.execute("select key, value from facts where user=?", (user,))}
    hot["scratch"] = []

def end_call():
    hot.clear()

remember("u42", "preferred_contact", "email"); remember("u42", "asset", "LT-4471")
start_call("u42", "Is my laptop under warranty?")
hot["scratch"].append("look up the warranty for LT-4471")
print("hot during the call:", hot)
end_call()
print("hot after the call :", hot)
print("cold (kept)        :", cold.execute("select key, value from facts").fetchall())

Output (from running the code above):

hot during the call: {'question': 'Is my laptop under warranty?', 'profile': {'asset': 'LT-4471', 'preferred_contact': 'email'}, 'scratch': ['look up the warranty for LT-4471']}
hot after the call : {}
cold (kept)        : [('preferred_contact', '"email"'), ('asset', '"LT-4471"')]

What to watch for.

  • Load only what the call needs from cold state (what is saved in a database for later), not everything about the user.
  • Decide explicitly what gets written back; scratch work usually shouldn't.
  • Cold state (what is saved in a database for later) holds personal data; protect and expire it.

In plain terms: take the one file you need out of the cabinet, work on it, file the result, clear the desk.

In NurseOps Now

Built. Hot = the window built per call; cold = SQLite (cases, reviews, decisions, audit (a permanent record of who did what and when)), LangGraph (a tool for building AI workflows step by step) checkpoints (saved copies of a conversation's state) for chat, and Chroma (the database that stores the policy vectors) for policies (the health plan's written rules for when tests are covered). See the Intro and Step 1.

Trade-offs

  • Cold reads add latency (how long it takes to respond); cache hot items that repeat.
  • Two places for state (everything the app must remember to continue correctly) means a clear rule for what goes where.

Interview answer

"I split memory into hot state (what is in the current AI call) for the current call and cold state (what is saved in a database for later) in a database. Each call loads only what it needs from cold storage, does its work in memory, and writes back what should be remembered, so restarts and new sessions lose nothing."

All data in this post is made up. No real people, tickets or patient data.
